# Cross-agent configuration profiles

> Design and acceptance contract for named, explicitly captured multi-agent profiles ("bundles"). Reconciled with the target repository's current implementation, not a record of a completed desktop or upstream acceptance run. See the [profile guide](../guides/profiles.md) for user-facing precautions.

## Purpose and entry points

A profile saves a repeatable combination of provider selections, model choices and supported resource assignments across selected agents. Typical uses include work/personal setups or different cost preferences; a profile does not change upstream pricing or make an incompatible provider protocol work. Configure and verify providers individually before capturing them. The provider editor, not the profile, owns endpoints, credentials and upstream protocol adaptation.

From the top-bar profile menu, create a named profile, choose the multi-agent profile option, and select **at least two agents with configured providers**. Applying a bundle opens a preview before writing; it is not a tray shortcut. The manager can rename a profile or **update its snapshot from current configuration**. Updating recaptures _all previously selected agents_, not additional agents; inspect each agent first. A single-agent switch does not rewrite the saved multi-agent snapshot. Existing single-agent profiles and older bundles remain compatible; legacy single-agent auto-save behavior is separate.

The agent selector derives availability from `src-tauri/src/services/profile_bundle.rs::agents`: it lists the supported application types, shows per-agent capabilities, disables agents without configured providers, and disables DoubaoWork because it has no managed switchable provider. Claude Desktop support is macOS/Windows only, not Linux. Currently supported capability groups are:

| Agents                                                    | Provider/model                                                  | MCP | Skills | Instructions                           |
| --------------------------------------------------------- | --------------------------------------------------------------- | --- | ------ | -------------------------------------- |
| Claude Code, Codex, Gemini, Grok Build, OpenCode, Hermes  | Yes                                                             | Yes | Yes    | Yes                                    |
| OpenClaw                                                  | Yes                                                             | No  | No     | Yes                                    |
| Pi                                                        | Yes, including native defaults/enabled models/reasoning options | No  | Yes    | Yes, including native prompt templates |
| Claude Desktop (macOS/Windows)                            | Yes, including model routing                                    | No  | No     | No                                     |
| WorkBuddy, Qoder CN, Kimi Code, Qwen Code, ZCode, TRAE CN | Yes                                                             | No  | No     | No                                     |
| DoubaoWork                                                | Native login/bridge only; selector disabled                     | No  | No     | No                                     |

Capabilities refer only to Vary AI-managed adapters, not all features of those clients. Profiles do not switch login accounts. For additive-provider clients, capture the managed enabled-provider set and each provider's models without deleting unmanaged native providers/resources. Common MCP/Skill definitions stay in the shared resource library: the snapshot stores references and enabled assignments, and apply uses the definitions current at apply time. Model lists, native defaults, enabled MCP/Skills/prompts, instruction-file contents and supported native selections are captured as applicable. Uncaptured legacy fields must remain untouched; a captured empty resource selection can clear managed assignments. Provider IDs, not provider brand names, identify saved selections. New providers are not automatically added to existing profiles; missing referenced providers fail rather than silently substituting another provider. Saved model choices are distinct from the provider's current endpoint, protocol and credentials. Treat profile data and exports as private; consult the [profile guide](../guides/profiles.md) about other profile categories that may include credentials.

## Preview, apply and recovery

- Preview shows each selected agent's current and target providers, models and managed resources, plus new-session/restart or separate client-sync guidance. Selectively changed providers and resources invalidate the preview: the revision covers the saved bundle, current providers and pointers, managed assignments/definitions, instruction files, Skill sources and native files. Re-preview on conflict; do not overwrite external edits. This is optimistic validation, **not** a cross-process file transaction or crash/power-loss atomicity guarantee.
- Apply validates targets, acquires agent locks in a stable order and applies every selected agent. On local failure it restores attempted agents in reverse order, including managed resource projections and native files, and reports rollback or restoration failure explicitly. On success the preview closes and a notification reports the result; refresh shared resources once. Unchanged agents may reuse the last successful apply only if the selection and complete local fingerprint still match. Codex restoration respects OAuth token refresh protection rather than overwriting a newly refreshed same-account token.
- The profile menu offers **undo last switch** for the latest successful bundle apply in this application process only. Undo checks for intervening changes before restoration; restarting the application expires the record. A later external edit must be preserved and reported as a conflict. Client restart/new session may still be required to load the new configuration.
- TRAE capture, preview, local apply and undo must work while disconnected; only after local apply or restore does the bridge attempt delivery to a connected client. Failed delivery records and displays _client sync pending_, without rolling back local changes; reapplying after reconnect retries delivery. Sync only touches Vary AI-managed model configuration, and must not start a client, install a bridge, enable auditing or export login credentials. Bridge connection/audit lifecycle locks are separate from local switching locks. Local success does **not** prove a real upstream request succeeds.

## Acceptance scenarios

Use synthetic provider/model data and an isolated HOME/temp directory, never real accounts or installed clients:

1. Configure two agents with provider/model set A, save a Work bundle; configure set B and save Personal. Preview and apply Work, inspect each native configuration, then apply Personal. Verify nonselected agents do not change; a single-agent switch changes only that agent and does not modify either snapshot.
2. Rename Personal, update its snapshot after changing selected agents, and repeat both directions. Verify explicit refresh captures only the saved agent set. Reapplying a saved bundle should restore its captured values without cloning provider secrets.
3. Confirm MCP/Skill/instruction assignment and native model behavior for each supported capability, captured-empty versus omitted legacy fields, additive providers, Pi template/native selection, managed backups while routing, and backward compatibility. Verify 14 file-based provider-capable agents plus offline TRAE; this does not establish real-client coverage for every login.
4. Edit a native file or provider/resource definition after preview: apply must reject without overwriting it. Edit after apply: undo must reject and preserve it. Inject a second-agent switch or resource projection failure: prior agent files, database pointers and managed resources must recover, or a restoration failure must be reported.
5. Test TRAE offline preview/apply/undo, disconnect after preview, reconnect and reapply, and simulated bridge delivery. Repeat the same bundle to check unchanged-agent reuse; external changes must defeat reuse. Use isolated fixtures for invalid Codex account and Skill sources.
6. For a real desktop walkthrough, use already validated providers, apply Work/Personal through the preview and verify with **new client sessions and real requests**. Protocol compatibility (including a full Codex Responses-to-Chat-Completions tool-call/streaming path) requires separate end-to-end evidence; a minimal probe and successful local profile apply are insufficient.

## Current implementation and verification boundary

The target already has `src-tauri/src/services/profile_bundle.rs` (capture, preview, apply, undo), `src-tauri/src/commands/profile.rs`, `src/components/profiles/{ProfileSwitcher,ProfileBundleDialog,ProfileManageDialog}.tsx`, and synthetic integration scenarios in `src-tauri/tests/profile_bundle.rs`. These paths are implementation pointers, not proof that every scenario above was run for this documentation change. The existing [profile guide](../guides/profiles.md) also covers the broader, legacy profile entity; it should not be read as a guarantee that bundle previews copy credentials. To rerun the integration tests, use an isolated test HOME according to the repository's testing conventions, then `cargo test --test profile_bundle --manifest-path src-tauri/Cargo.toml`; run the repository checks in `AGENTS.md` before claiming broader implementation acceptance. Do not launch or replace a running desktop app as a routine check. No historical test counts, temporary demo app or past live upstream result is asserted here.
