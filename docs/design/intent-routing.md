## 1. 核心方案

新增一层由用户明确启用的意图路由：在符合条件的新用户轮次开始时识别任务类型，从用户配置的供应商和模型中选择优先目标。

**意图识别只提供路由建议，不能覆盖鉴权、DLP、协议兼容性、账号边界、用户明确指定的模型，以及会话续接安全要求。**

首版客户端已确定为 Codex；其余兼容性范围建议如下：

- 优先跑通 Codex 的 `/v1/responses` 请求；首版自动路由建议仅纳入 API Key 供应商及原生 Responses 上游。
- 引入 Codex 范围内的多个扁平路由组；每组独立配置模型成员、具体默认目标、分类器和意图规则。
- 用户用自然语言描述意图，单独配置负责分类的小模型。
- 每个可确认身份的用户轮次只识别一次；工具回传保持实际处理本轮请求的上游绑定。
- 提供配置、真实分类试跑和脱敏决策记录。
- 保留客户端原有推理强度，首版不自动调整。

Claude Code 和其他客户端延后接入。Codex 的 `previous_response_id`、工具回传和账号边界属于首版必验项，不能留到后续兼容阶段。官方账号继续保持既有直连/转发行为，但建议首版不作为自动路由组成员。

此前的界面演示已丢弃。当前已在“设置 → 路由”实现真实草稿编辑与扩展库存储，支持模型成员、默认及后备目标、意图规则、分类器配置及离线目标顺序校验。保存与删除使用版本检查，导入后强制关闭，禁止真实启用。成员和规则暂存于单个组配置 JSON 中，扩展库版本为 4，共享库版本不变。

已增加默认关闭的“自动创建路由组”开关：根据已保存的 Codex 模型目录，按完全相同的模型 ID 聚合至少两个合格供应商；自动组动态派生，编辑保存后保留为手动组，删除后隐藏。目录刷新不覆盖用户修改；此功能不启用真实转发。

真实分类调用、运行时快照、轮次绑定、Auto 模型目录、Codex 转发和决策记录仍未实现；下文仍是完整目标方案，不能视为已完成验收。离线校验只接受手工输入的虚构分类 JSON，不代表自然语言意图识别。

## 2. 目标与非目标

用户应能够描述“什么任务交给哪个模型”，测试策略，明确启用，并了解每次决策的原因。成功标准是路由行为可预测、额外开销有上限，而不是保证识别永远正确或费用一定降低。切换模型可能损失提示词缓存收益。

首版不包含：

- 静默覆盖用户指定的具体模型、自动接管全部代理流量，或在官方账号及托管 OAuth 账号之间自动切换。
- 嵌套路由组、向量索引、分类器训练、自动发现供应商或持久化完整会话。
- 对原始工具参数、工具结果、图片、附件、思考内容或系统指令进行意图分类。
- 自动修改推理强度，或改变现有安全决策、重试上限与响应语义。

从用户视角看，分类不是后台异步操作：缓存未命中时，业务转发需要在限定时间内等待分类结果。

必须解决的差距：

- `select_providers` 返回供应商，而不是精确的 `(provider, model)` 目标，仅重新排列供应商不能实现完整意图路由。

## 4. 请求处理流程

```text
现有请求准入与安全决策
  → 明确识别 Auto 请求，并解析具体默认目标
  → 检查会话续接身份及请求是否可安全转移
  → 复用本轮计划，或提取受支持的用户文本
  → 执行分类器专用安全脱敏
  → 筛选候选意图，并在时限内分类
  → 严格校验结果，生成具体目标计划
  → 执行现有协议转换、转发和重试
  → 异步记录脱敏决策及用量
```

分类结果只能改变已批准目标集合内的优先顺序，不能授权新的端点、账号、凭据、协议转换或工具执行。

## 5. 配置结构与明确启用

### 5.1 路由组与组内策略

供应商管理负责地址、凭据、协议和模型；路由组引用现有供应商模型，不创建新的凭据副本，也不是一种新供应商类型。

每个组拥有独立策略。下文的“策略版本”“策略默认目标”均指所在路由组的配置，不再表示每个客户端只能有一个策略。首版允许同一个模型被多个组引用，但不支持组嵌套或跨客户端组。

| 字段                       | 含义                                                         |
| -------------------------- | ------------------------------------------------------------ |
| `id`、`name`、`revision`   | 稳定组 ID、展示名称和单调递增的配置版本                      |
| `enabled`、`client`        | 组默认关闭；首版客户端固定为 `codex`                         |
| `autoModelId`              | Vary AI 管理、客户端可选择的组别名                           |
| `members`                  | 成员 ID 对应明确的供应商 ID 和上游模型 ID                    |
| `defaultMemberId`          | 未命中或分类失败时使用的组内默认成员                         |
| `fallbackMemberIds`        | 组内明确批准的有序后备成员，不复用全局队列                   |
| `intentRecognitionEnabled` | 组内意图识别开关，与组启用开关独立                           |
| `classifierTarget`         | 具体分类器供应商和模型，可不属于组内成员，但不能指向另一个组 |
| `rules`                    | 组内有序规则，使用稳定意图 ID 和组内目标引用                 |
| `failurePolicy`            | 默认 `default_target`，可选 `previous_if_eligible`           |
| `classificationBudgetMs`   | 建议默认 2,000 毫秒，可配置范围 500–5,000 毫秒               |
| `privacyPolicyVersion`     | 分类器文本提取和脱敏策略版本                                 |

每条规则包括 `id`、`name`、`description`、`enabled` 和 `targetMemberIds`。规则目标、默认目标及后备目标只能引用本组成员。首版界面可以仅提供一个规则优先目标，模型身份不能使用展示名称代替。

组已启用但意图识别关闭时，使用组内默认目标和批准的后备顺序，不调用分类器。组本身关闭时，不接受新组请求；明确报错并提示选择具体模型或重新启用，不能暗中启用组。现有绑定按第 7 节安全结束。

以下为使用虚构 ID 的示例：

```json
{
  "id": "group-development",
  "name": "日常开发",
  "revision": 1,
  "enabled": false,
  "client": "codex",
  "autoModelId": "vary-auto/group-development",
  "members": [
    {
      "id": "balanced",
      "providerId": "example-provider",
      "modelId": "default-model"
    },
    {
      "id": "strong",
      "providerId": "example-provider",
      "modelId": "strong-model"
    }
  ],
  "defaultMemberId": "balanced",
  "fallbackMemberIds": ["balanced"],
  "intentRecognitionEnabled": true,
  "classifierTarget": {
    "providerId": "example-classifier",
    "modelId": "small-model"
  },
  "classificationBudgetMs": 2000,
  "failurePolicy": "default_target",
  "privacyPolicyVersion": 1,
  "rules": [
    {
      "id": "intent-tests",
      "name": "测试与调试",
      "description": "编写回归测试、排查失败原因并修复缺陷。",
      "enabled": true,
      "targetMemberIds": ["strong"]
    }
  ]
}
```

候选顺序按优先目标、后备成员、默认成员生成，并按成员身份去重；同一成员不能因重复引用而被额外重试。

### 5.2 Auto 请求准入与默认回退

建议以 `vary-auto/<group-id>` 这样的虚拟模型作为明确选择入口，但必须先验证客户端模型目录及选择能力。该格式目前是方案，不是应用已经对外提供的模型。

保存或启用策略不能静默接管客户端，也不能自动替用户选择 Auto。用户需通过受支持的客户端集成，单独启用本地路由并选择 Auto。涉及客户端配置写入时，必须检查配置归属并支持恢复原设置。

明确指定具体模型的普通请求绕过意图路由。通用模型名称或缺少模型字段，不代表用户允许自动路由。

分类前必须先解析具体默认目标。分类失败时使用该目标，不能向上游发送虚拟别名：

- 普通请求：保持既有路由行为。
- 已接受的 Auto 请求：没有意图命中时，使用策略配置的具体默认目标。
- 未知 Auto 别名或缺少默认目标：返回固定、符合协议格式的配置错误，不转发未解析别名。

### 5.3 Codex 首版协议边界

首版最小闭环是：创建 Codex 路由组 → 加入可用的原生 Responses 模型 → 配置默认成员和分类器 → 添加意图规则 → 手动试跑 → 开启 Codex 本地路由并选择组别名 → 真实请求命中目标 → 工具续接成功 → 查询实际决策。

- 客户端继续使用 Responses 协议，不能为实现路由而把 Codex 的 wire protocol 改成 Chat Completions。
- 通过现有 Codex 模型目录能力暴露组别名，保留用户自定义目录内容。必须验证目录显示、实际选择、请求携带别名及恢复具体模型四个环节；不能仅凭 `/v1/models` 成功断言接入完成。
- 首版纳入自动路由的目标建议限定为原生 Responses API Key 供应商。现有 Responses → Chat/Messages 转换不受影响，但暂不作为组内动态选模的验收范围。
- 从 `input` 字符串或受支持的用户消息 `input_text` 提取意图文本；`instructions`、`function_call` 参数、`function_call_output`、reasoning 和加密内容不进入分类器。
- 不覆盖客户端 `reasoning.effort`、工具定义及其他参数；目标不支持请求要求时应剔除，而不是偷偷降级参数。
- 官方账号携带原生鉴权的请求保持原账号边界，不把它的 token 发送给组成员或分类器。
- `/v1/responses/compact` 属于会话维护请求，不作为新用户意图；若携带组别名，需使用已知有效绑定解析到具体目标，无法安全续接时返回固定错误，不能随机改选模型。
- 首版主链路为 HTTP JSON/SSE。WebSocket 等其他传输不因名称同为 Responses 就自动获得支持；客户端实际使用路径必须在接入验证中确认。

### 5.4 Codex 的续接与切换条件

`thread-id` 等会话身份和 `previous_response_id` 的作用不同：后者是上游响应游标，不是稳定会话 ID。沿用 `session.rs` 的区分，新增路由绑定，不能把游标直接当作会话身份。

| 请求情况                                         | 首版处理                                                                             |
| ------------------------------------------------ | ------------------------------------------------------------------------------------ |
| 新用户轮次、无供应商绑定状态、上下文完整且可迁移 | 可以识别意图并在组内选择目标                                                         |
| 带已知 `previous_response_id`                    | 固定到生成该响应的实际供应商、账号和模型，不跨上游发送游标                           |
| `function_call_output` 工具回传                  | 使用响应 ID 或已验证调用关联找到本轮绑定，不重新分类                                 |
| 未知游标、未知调用关联、无法验证的签名或加密状态 | 不靠分类猜上游，不自动回放缺失历史；采用经过验证的保守续接路径，否则返回固定续接错误 |
| 新用户轮次但仍携带上游绑定状态                   | 连续性优先，不能因为是新轮次就跨模型切换                                             |

从 JSON 响应及 SSE 响应事件中有界地观察响应 ID、调用关联和实际目标，维护内存绑定，不改变原始流内容，也不缓存完整回复。观察失败不能打断当前成功转发，但下次缺少绑定的续接必须保守处理，不能猜测。

现有 `providers/codex_chat_history.rs` 主要解决 Chat 桥接历史，不能当作原生 Responses 跨供应商迁移的通用保证。首版不实现跨供应商历史重建。

若首次实测发现 Codex 始终以绑定游标续接，应如实展示“会话绑定，暂不切换”。必须至少证明受支持的可迁移新轮次能够产生不同意图对应的目标选择；仅首轮选模、后续永远固定不能当作逐轮意图路由全部验收通过。

## 6. 意图识别约定

### 6.1 可使用的上下文

从请求中生成只读的分类视图，不序列化完整请求，也不为方便分类而修改业务转发正文。

| 输入             | 建议上限                              | 限制                       |
| ---------------- | ------------------------------------- | -------------------------- |
| 当前真实用户文本 | 4,000 个 Unicode 标量值               | 保留前 3,000 和后 1,000    |
| 上一条用户文本   | 1,000 个标量值                        | 必须来自同一会话           |
| 上一轮助手回复   | 1,000 个标量值                        | 仅纯文本，优先保留结尾     |
| 上一轮意图       | 一个仍适用的 ID                       | 作为辅助上下文，不作为指令 |
| 候选意图         | 最多 16 个，每个描述最多 500 个标量值 | 使用稳定 ID，并校验描述    |

编码后的分类器输入最多 32 KiB。超出时优先移除可选的历史上下文，不能静默截断 ID 或 JSON 结构。无法构造安全且有界的输入时，跳过分类。以上上限需通过基准测试确认。

按协议和客户端分别提取文本，排除工具、推理、附件、系统指令及已知注入通知。不能用过宽的规则删除用户自行编写的标签。无法分清用户内容与工具结果、或遇到不支持的结构时，应安全跳过，而不是猜测。

只有图片的请求通过能力筛选和默认路由处理，不进行文本意图猜测。

### 6.2 模型调用与返回值

选择明确的低延迟分类模型。首版支持经过验证的 Chat 兼容分类器，其协议与任务模型的转发协议相互独立。

分类调用必须使用分类器自己的凭据和端点限制，不能复用入站请求的 Authorization。

指令、候选描述和会话摘录要分开组织。会话摘录是不可信数据，不是指令。真正可执行的提示注入防线，是模型之外的意图 ID 校验和目标白名单。

优先使用结构化输出约束；不支持时严格解析 JSON：

```json
{ "intentId": "intent-tests" }
```

`{"intentId":null}` 表示不命中。拒绝未知 ID、额外字段、多个对象、超长返回和解释性文本。不能从任意模型回复中取第一个数字作为分类结果。

诊断只记录固定错误码，不记录格式错误的原始回复。输出 token 数和响应字节数分别设限。

不能把聊天模型自报的百分比当作经过校准的置信度。后续专用决策模型可以在测量阈值后引入置信度，首版不展示置信度仪表。

### 6.3 规则匹配

1. 按客户端范围、授权、账号边界、协议、工具及图片能力、已知上下文上限和续接约束筛选目标。
2. 排除没有可用目标的规则，收集剩余意图 ID。
3. 仅在能够确认新用户轮次且存在候选意图时调用分类器。
4. 根据本次候选集合与配置版本严格校验分类结果。
5. 为返回的 ID 选择第一条启用且适用的规则。
6. 生成具体目标计划及明确批准的回退候选。

一次请求只选择一个意图，不同时输出多个标签。优先级表示配置顺序，并不能保证分类器总能一致地区分重叠类别。界面应提示用户避免含糊或重复的意图描述。

后续若增加确定性条件，应先判断这些条件；前面的规则已经足以决定路由时，不再调用分类器。

## 7. 轮次保持与并发控制

会话请求头不是轮次 ID，而且可能由主代理和子代理共享。仅对最后一条用户消息做哈希，也无法区分不同轮次中的相同消息。

需要独立的适配器，结合客户端范围、策略 ID、真实会话身份、可用的分支或父请求身份，以及受支持的对话位置或明确消息身份。文本指纹使用临时密钥哈希；决策记录不持久化原始会话身份或文本指纹。

适配器返回 `new_turn`、`same_turn` 或 `unknown`。完整对话中，只有真实用户消息推进轮次，工具结果不推进轮次。增量请求必须能够关联已知的前序请求。生成 UUID 或猜测文本不能证明会话连续性。

```text
new_turn  → deciding → 优先目标计划
                     → 跳过、未命中或失败时的默认计划
same_turn → 保持实际上游绑定，不再分类
unknown   → 不按语义改选目标，保留续接限制
```

无法确认连续性时，仅在请求可安全转移的情况下使用具体默认目标。否则应保留已知上游绑定，或返回现有续接错误，不能把供应商绑定状态发给另一目标。

**新用户轮次是安全切换模型的必要条件，但不是充分条件。**

每轮决策必须原子提交。并发到达的同轮请求共享待完成的决策；旧轮次迟到的结果不能覆盖新状态。优先目标和实际成功上游分别记录。

工具续接应保持在实际发出工具调用的上游，包括故障转移后成功的上游，而不只是最初优先选择的模型。

策略修改只作用于新轮次；进行中的轮次在目标仍有效时固定使用旧快照。凭据撤销、供应商删除、安全策略变化和用户明确选模立即优先生效。

暂停分类不能在工具执行中途清除必要的续接状态。存在尚未结束的绑定时，界面显示“等待现有轮次结束”。缓存淘汰或应用重启意味着连续性丢失，不代表可以重建隐藏的上游状态。首版不持久化会话摘录及轮次状态。

## 8. 转发与重试语义

引入类型明确的 `RoutePlan`，包含每个候选的供应商与模型身份、策略版本、来源及脱敏决策信息。不能把每次意图选择写成全局当前供应商，也不能逐请求修改客户端配置。

需检查现有故障转移切换的副作用：意图路由选中的目标成功后，不应静默触发全局供应商切换或无关通知。

模型选择优先级：

1. 用户明确指定具体模型：保持现有行为，不接受意图覆盖。
2. 已接受的 Auto 请求：使用候选中经过校验的精确模型。
3. 执行必要的供应商规范化和协议转换，但不能替换为无关默认模型。

每次重试使用对应候选的凭据及模型 ID，不能把第一个供应商的模型 ID 传给全部后备供应商。只有真正发起上游请求时才获取熔断器放行许可，并且每次许可只释放一次。

策略目标是独立、明确批准的候选范围，不是静默加入全局故障转移队列。复用现有重试机制，不意味着现有供应商选择接口已经支持此能力。

策略默认目标在仍然适用时作为最终批准的回退目标。如果没有批准的目标可用，返回正常可用性错误，不突破账号边界。绑定供应商状态的工具续接，比无状态新轮次具有更严格的故障转移限制。

保留无关请求头、协议字段、工具 ID、模型参数、取消行为、JSON/SSE 语义和响应结构。用量记录区分请求中的 Auto 别名、优先模型、实际出站模型和供应商返回的模型，不能为了隐藏路由选择而改写响应模型字段。

首版保留推理设置。后续覆盖推理强度，必须有明确配置、模型能力校验，以及缓存和协议回归测试。

## 9. 延迟、资源上限与异常回退

以下是建议默认值，不是已验证的性能承诺：

| 机制                      | 建议                                                    |
| ------------------------- | ------------------------------------------------------- |
| 分类时限                  | 默认 2 秒；等待、传输、解析和任何重试共享同一个预算     |
| 结果缓存                  | 硬上限 1,024 条，有效期 5 分钟                          |
| 轮次绑定                  | 硬上限 2,048 条，空闲有效期 30 分钟；活动租约也需要上限 |
| 并发去重（single-flight） | 相同且已校验的输入共享正在进行的分类调用                |
| 分类器并发                | 最多 4 个；排队消耗同一个分类时限                       |
| 故障冷却                  | 传输、超时或鉴权失败后，按分类器配置版本冷却 30 秒      |
| 响应限制                  | 严格结构，正文最多 4 KiB，同时限制输出 token 数         |

缓存键包含策略版本、分类器供应商和模型及配置版本、隐私策略版本、候选 ID 与描述、脱敏后的当前及历史上下文、上一轮意图。首版只在同一策略和会话内复用。相关配置修改后失效，不能仅以模型名称作为缓存身份。

每个等待者具有独立的截止时间和取消状态。一个请求断开连接不能取消其他仍在等待的请求所需的共享调用；没有等待者时取消上游调用。不能持有数据库锁或长期互斥锁跨越异步等待。

| 情况                              | 处理方式                                                      |
| --------------------------------- | ------------------------------------------------------------- |
| 没有意图命中                      | 使用策略的具体默认目标                                        |
| 模型输出非法                      | 固定错误码 `invalid_output`，回退默认目标；重复错误需有界冷却 |
| 分类超时或分类器不可用            | 使用默认目标；仅在用户明确配置时复用仍适用的上一轮意图        |
| 摘录缺失或无法安全脱敏            | 跳过分类，不能外发未脱敏文本                                  |
| 工具续接                          | 保持有效的实际上游绑定，不调用分类器                          |
| 明确指定模型或账号                | 绕过自动路由                                                  |
| Auto 或默认目标配置非法           | 固定配置错误，不转发虚拟别名                                  |
| 审计队列满或持久化失败            | 继续转发，增加记录丢弃计数                                    |
| 业务请求被 DLP 阻止或无法安全脱敏 | 保留原安全决策，不允许分类器绕过                              |

话题变化后，复用上一轮意图可能出错，因此默认关闭，并在决策记录中明确展示。分类器自身失败不能导致原本可正常转发的业务请求失败。

## 10. 隐私与安全

分类会向额外目的地披露部分内容。首次启用及分类器目的地变化时，必须说明这一点，并要求用户明确操作。可以提供本地分类器，但不能把远程模型描述成本地处理。

所有外发文本都要应用分类器专用安全脱敏，包括规则描述和上一轮助手上下文。业务路由的“仅审计”许可，不代表允许向另一个分类器披露原文。无法确认安全脱敏时跳过分类调用，但不能弱化业务请求本身的安全失败处理。

使用内部类型化的请求来源标记防止递归分类，不能仅依赖客户端可伪造的 User-Agent。限制内部调用数及载荷大小。分类器不能返回待执行的 URL、凭据、命令或供应商 ID。

运行记录只持久化标识、枚举、计数和耗时，不保存提示词、回复、原始工具内容、请求体、敏感命中、会话 ID 和供应商原始错误。用户自定义名称及描述属于配置，不天然属于安全日志。临时密钥哈希可以降低关联风险，但不等于匿名化保证。

## 11. 存储与模块划分

本功能配置和记录放入扩展库 `vary-ai.db`，通过稳定 ID 引用共享供应商，不复制凭据。

建议数据表，具体名称需经迁移评审：

- `intent_routing_groups`：客户端范围、组信息、默认及后备成员引用、带版本的组内策略配置。
- `intent_routing_rules`：所属组 ID、规则顺序、稳定意图 ID 和目标成员引用。
- `intent_routing_members`：所属组 ID、稳定成员 ID，以及批准的供应商和模型引用。
- `intent_routing_decisions`：脱敏、有保留上限的决策记录。

实现时检查实际 schema 后再选择下一扩展迁移版本，保留共享库兼容性。明确备份、导入和导出行为，校验失效引用；导入策略不能自动启用，决策历史默认不同步。

配置命令在转发链路之外持久化配置、解析供应商引用，然后向 `ProxyState` 发布不可变快照。更新失败保留上一个有效快照，供应商变化使相关快照和缓存失效。

请求侧只读取快照和有界内存状态；决策与用量写入异步队列。后台工作同时需要两个数据库连接时，先锁共享库，再锁扩展库。

建议新增模块：

```text
src-tauri/src/services/intent_routing/       配置和快照管理
src-tauri/src/proxy/intent_routing/          提取、分类、轮次与路由计划
src-tauri/src/database/dao/intent_routing.rs 扩展库持久化
src-tauri/src/commands/intent_routing.rs     类型化界面命令
src/components/routing/                     页面和编辑器
src/lib/api/intentRouting.ts                前端 API 绑定
src/types/intentRouting.ts                  前端类型约定
```

以上是建议新增路径，不是已存在模块。

状态需明确区分：未配置、配置就绪但未启用、已启用、客户端未选择 Auto、分类器降级，以及等待现有轮次结束。代理监听器运行，不足以证明 Auto 路由正在生效。

### 12.1 首次配置

1. 打开“设置 → 路由”，在 Codex 下创建路由组，引用现有供应商模型，检查本地路由是否就绪。
2. 从组内成员选择具体默认目标和批准的后备顺序。
3. 选择分类器，查看数据披露和费用说明。
4. 新增任务类别，或编辑少量预设模板。
5. 测试组内规则，再明确启用路由组及意图识别。
6. 在 Codex 选择该组 Auto 别名，验证真实请求，并提供恢复原具体模型的方法。

未知模型能力必须标注并在生产使用前验证，不能直接显示为已确认兼容。试跑失败不应破坏现有代理，也不应强制改变用户当前模型。

### 12.2 路由规则

规则行展示优先级、意图名称与描述、供应商和模型、启用开关及编辑入口。列表下方单独展示默认目标，说明未命中时的处理。

即使支持拖拽排序，也需提供键盘可操作的排序方式。

编辑器包含名称、任务描述、目标和启用状态。校验空内容、重复项、供应商缺失及能力不支持等情况。保存时明确“仅对新轮次生效”。首版推理强度显示“保持客户端设置”，不提供未实现的自动推理控件。

### 12.3 消息试跑

必须清晰区分两种模式：

- **本地演示**：使用固定虚构场景，不发网络请求；不能让任意输入看起来获得了真实分类结果。
- **真实分类测试**：由用户明确触发分类器调用，说明会发送脱敏文本及可能产生费用；只分类和解析路由，不调用最终任务模型，也不修改生产轮次状态。

允许可选的上一轮上下文。展示文本提取或跳过结果、命中规则、优先目标、回退原因和实测分类耗时。不编造置信度、节省金额，也不采用模型生成的路由解释作为事实。

配置修改后，旧测试结果标记为已过期。取消测试后，迟到结果不能覆盖后续新测试。

### 12.4 决策记录

展示时间、客户端、规则 ID、优先目标与实际目标、分类器状态、耗时、缓存命中或轮次保持或回退状态，以及策略版本。区分手动测试和真实流量。

详情只展示原因码，不显示原始会话内容。提供空态、加载态、错误态、有界分页，以及需要确认的按筛选条件删除操作。记录丢弃应可见，不能把不完整历史呈现为完整记录。

运行界面继续通过现有语言文件支持 `en`、`zh`、`ja` 和 `zh-TW`。本文按本次要求使用中文，不改变项目其他文档、设计资产、截图及代码注释的语言约定。窄屏下将规则信息和试跑结果纵向排列，不能隐藏关键操作。

## 13. 测试先行的实施阶段

### 阶段 0：确认约定

客户端已确定为 Codex；确认供应商范围、组成员引用、Auto 选择语义、具体默认目标、隐私披露和界面流程。准备新轮次、子代理、工具结果和上下文压缩的虚构协议样例。本文不代表尚未确认的选择已获准实现。

### 阶段 1：策略与纯决策核心

先编写配置校验、候选筛选、明确选模绕过、严格 JSON 解析及逐候选精确模型测试，再添加扩展库迁移、类型化命令和不可变快照。自动路由保持关闭。

### 阶段 2：分类与轮次安全

连接传输前先编写文本提取和脱敏测试。实现截止时间、取消、硬容量缓存、并发去重、冷却和轮次原子状态。

覆盖相同消息重复出现、会话分支、并发请求、旧结果迟到、身份缺失、配置版本变化、供应商删除、重启及状态淘汰。

### 阶段 3：Codex 真实转发闭环

接入 Codex 原生 Responses 和 API Key 供应商。测试组别名的模型目录、选择与恢复、每个候选的凭据及模型，以及熔断器许可的完整生命周期。

首版必须覆盖 `input` 字符串与消息数组、`previous_response_id`、`function_call_output`、JSON/SSE 响应身份、压缩请求、并发分支和缺失续接绑定。证明完整工具循环可执行且不重复分类，证明可迁移的新轮次可按意图切换，而绑定轮次不越界。

分类不能进入重试循环，意图决策不能产生全局供应商切换副作用。使用本地模拟上游验证 JSON、SSE 和取消行为。

### 阶段 4：界面与验收

基于现有应用外壳实现已确认页面。测试表单校验、启用前提、语言覆盖、过期与取消的测试结果、历史状态、键盘操作和窄屏布局。

界面评审使用隔离的 renderer 预览，不启动已安装应用，也不触碰真实客户端配置。

### 阶段 5：扩展兼容性

Codex 首版通过后，再接入 Claude Code 和其他客户端。官方账号组成员、Responses 跨协议目标、WebSocket 传输和跨供应商历史重建分别评审，不能通过放宽续接约束来扩大支持范围。

其他客户端、嵌套组、推理覆盖和专用决策模型适配器分别立项。供应商出现在界面中，不代表已经满足意图路由条件。

## 14. 验证与验收标准

统计分类器调用次数、缓存命中、超时及非法输出及冷却比例、优先与实际目标差异、额外延迟、分类用量和审计丢弃数。

在同一组虚构工作负载上，与关闭路由的情况比较总费用和首字延迟，并计入目标切换导致的提示词缓存损失。

验收标准：

- 策略关闭和明确指定模型的请求保持既有行为。
- 已接受的 Auto 组别名只解析到本组批准的具体目标，组间不串用规则和默认目标。
- Codex 实际完成组别名选择、不同意图选模、工具调用与回传、SSE 输出以及分类超时回退的闭环；不能只用静态演示替代。
- 已知游标固定到实际目标，未知游标不发送到随机目标；压缩请求不触发意图分类。
- 工具续接不重新分类，也不迁移不可安全转移的供应商绑定状态。
- 分类失败的额外等待限制在配置预算及实测调度开销内，不单独导致正常业务转发失败。
- 分类器或审计失败不能绕过 DLP 和账号边界。
- 载荷保真、流式响应、取消和用量归属具有回归测试。
- 界面区分已保存配置、客户端选择 Auto 和实际观察到的路由。
- 本地虚构结果和真实分类结果不会混淆。

使用虚构测试数据、临时目录、内存数据库和动态端口。不能使用生产凭据、占用正在运行的代理默认端口，或把启动、安装、替换用户应用作为常规验证方式。

功能实现阶段按仓库要求执行：

## 15. 待确认事项

**已确认：首版先跑通 Codex，Claude Code 不作为首版前置条件；入口放在“设置 → 路由”独立 Tab，现有本地路由整体迁入，意图识别在此基础上开发。**

1. 是否接受首版自动路由组仅纳入 API Key、原生 Responses 目标？官方账号和跨协议目标暂缓，既有普通请求行为保持不变。
2. 是否接受虚拟 Auto 模型作为明确启用入口？客户端目录与选模能力验证通过后才能确定最终协议约定。
3. 是否接受 Auto 请求配置具体默认目标，而不是使用含糊的“保持原路由”语义？
4. 是否接受分类器专用安全脱敏，以及无法确认脱敏时跳过分类，即便业务路由允许仅审计的文本原样转发？
5. 是否接受保留和导出默认值：本地保留 7 天、最多 10,000 条、不同步历史、默认不复用上一轮意图？
6. 在已确认的“设置 → 路由”入口内，是否接受多个 Codex 扁平路由组、组内意图规则，以及先配置和测试、后启用的流程？组嵌套和跨客户端组暂不支持。
