# Tool observations and risk evaluation

The current implementation observes supported tool-call payloads, normalizes the known tool semantics, evaluates applicable enabled rules and records sanitized results. It provides warnings and records, not execution authorization or a sandbox.

## Manual rule preview

The rule preview evaluates synthetic or user-entered tool arguments without executing a tool or recording a live observation. It remains available when live tool observation is disabled. Its results do not indicate that live protection is enabled; the panel explicitly identifies the disabled live-observation state. Malformed object, array or quoted JSON input is rejected before evaluation instead of being reinterpreted as plain text. Free-form inputs remain available. OpenAI `write_file` requires `path`; Claude and Gemini use `file_path`. An `unchecked` result indicates missing applicable evidence or rules, not a safety decision.

## Evidence boundaries

A model response describes a proposed call. It does not prove that a client selected or executed it, that permissions were granted, or that a later hook did not change the arguments. Provider-side execution must not be represented as local pre-execution evidence.

Parsing a tool name and JSON arguments is separate from understanding the tool's behavior. Coverage depends on the observed protocol, input completeness, known adapter, selected rule and available context. Unknown or out-of-scope operations must not be described as safe.

## Forwarding and privacy

Observation is a bounded side channel. It must not pause or rewrite ordinary streaming output, authorize commands, or interrupt forwarding when its own queue/worker fails. Keep raw tool inputs, secrets, untrusted names and model explanations out of ordinary diagnostics. UI records use the sanitized summary and explicit coverage/execution limitations.

Schema collection scans at most 1,024 total catalog entries, including expanded Gemini function declarations. Extension tools count toward this work budget but do not establish built-in semantics. Large supported catalogs retain recognized built-ins without copying tool descriptions or whole schemas. Duplicate aliases (including trimmed Codex aliases), custom namespaces, unsupported argument schemas and per-schema byte/depth overflow still refuse built-in attribution. Catalog overflow disables attribution for that response without interrupting forwarding.

WorkBuddy and WorkBuddy AI native `Bash` calls use separate trusted client schema references with a required string `command` field. Their shell calls use the same rule engine and command lists as Pi and Codex, while retaining the original WorkBuddy edition in event records. This does not register arbitrary OpenAI tools or WorkBuddy PowerShell semantics. A command is only warned about when an enabled rule or blacklist matches; `kubectl delete` is not an implicit Kubernetes destructive-operation rule. An explicit `kubectl delete` prefix blacklist can cover dry-run test commands without executing them during rule preview.

Qoder CN native `Bash` calls follow the same bounded schema validation and retain `qoder` as their event client. Kimi Code's native `Shell` and Qwen Code's `run_shell_command` also register required string `command` schemas and preserve their respective client identities. Shared-route registration also covers ZCode `Bash`, DeepSeek Harness `bash`, managed T3 Codex `exec_command`/`shell_command`, OpenCode `shell`/legacy `bash`, OpenClaw `exec`, Hermes `terminal` and Grok Build terminal tool/preset aliases. Each requires its own client schema reference and validated native input definition. Other Agent identities do not automatically inherit semantics merely because they use an OpenAI-compatible protocol or a similar tool name. The [full Agent coverage ledger](../qa/agent-feature-coverage.md) records the remaining gaps and distinguishes implementation from native acceptance; the overall feature is incomplete.

TRAE CN and International use separate warning-only native `PreToolUse` hooks for `RunCommand`, independent of text DLP and model routing. Edition-bound local credentials prevent cross-edition attribution. Only VaryAI's unchanged owned Hook entries are removed when consent or collection is disabled; existing user Hooks and native permission policies are preserved. Hook execution has a bounded observation timeout and returns no allow/deny decision. Client Hook settings or sandbox restrictions can prevent delivery and require native acceptance.

Doubao Work observes native-instance `Bash` calls through the installed background runtime's pre-execution lifecycle. It resolves that lifecycle by its source contract, retains only the command field and actual supplied conversation/call identity, and removes its observer on shutdown or reconnect. Missing native contracts degrade coverage without changing tool execution, signatures, request DLP or streaming. Shared queue item/byte limits, collection generations, sanitized projections, asynchronous persistence and notifications apply to native hooks as well as proposed model-response calls. Native evidence remains `client_hook` / `pre_execution`; it is never relabeled as a model proposal or completed execution.

Current Doubao Work versions execute tools in a separate native JSRuntime, which may not invoke that background lifecycle. A second, read-only CDP Network subscriber watches live `/chat/completion` SSE responses on the verified native chat/background pages. It accepts only completed shell operation cards (`block_type=10019`, general-task scene, shell content type) and the explicit `display_content.operation` field. Ordinary prose, echoed message history, code examples and tool results are not command inputs. Metadata supplies the real conversation ID (`doubaowork_` prefix); block IDs are item identities, never fabricated tool-call IDs.

This fallback emits `client_report` / `reported`, with a distinct validated shell-report schema, because the evidence is an execution report rather than a pre-execution callback. It can warn after execution; it does not block commands or claim prior approval. A working legacy hook takes precedence to avoid a second report notification. The transport bounds sessions, streams, chunk/line/command sizes and retention, handles buffered-data ordering and closed streams, and removes its own subscriptions on shutdown. It never changes permissions, native debugging origins, Fetch interception, request bodies or responses. Both operating systems use the same collector where a native audit connection exists; the Windows audit launcher remains unsupported.

The implementation is under [protocol observation](../../src-tauri/src/proxy/tool_observation) and [tool-risk services](../../src-tauri/src/services/tool_risk). Read their regression tests before extending an adapter or transfer rule.

The current worker uses static rules. No local-model reviewer is connected to the runtime. Persisted rule fields reserved by older configurations remain readable for compatibility.

Shell command list editors expose all five match scopes directly in the scope menu: prefix, program, exact, keyword and regular expression. Keyword and regular-expression validation and explicit scope confirmation remain required; there is no separate advanced-mode visibility switch.

Policy history shows localized built-in rule names and the current name of an existing custom rule beside its stable ID. Names come from current configuration, not a historical snapshot; deleted rules retain their IDs without inventing a name. Manual refresh reloads both history and current rule names, keeps refresh and clear actions disabled until both reads finish, and reports failure if either read fails without exposing backend error details. Saving identical settings does not advance the policy version or announce an update; real changes still apply when live observation is disabled.

Tool-event session IDs come only from a recognized client request session field or header, carried alongside the bounded response observation. IDs must be nonempty, at most 256 bytes and contain no whitespace or control characters. Missing or invalid IDs remain absent; generated routing identities and historical events are never relabeled as client sessions. The asynchronous worker persists the optional ID and the unified security-event list exposes it without copying raw tool arguments.

Pi 1.5.2's official `before_provider_headers` hook can supply the current native session-manager ID even on Gemini requests that omit provider session metadata. Active Pi connection synchronization installs the isolated `extensions/varyai-session-id.js` helper in the configured Pi agent directory. Gateway startup also repairs a missing helper for an active Pi connection independently of model-catalog publication, including when the gateway is already running. Unconnected and suspended shared connections do not trigger installation. It leaves existing configuration and extension files untouched, never overwrites an unexpected file at its own path, and becomes inactive outside local VaryAI Pi routes. The helper must be loaded by restarting Pi or using its native resource reload. It stores no session IDs, reads no histories or credentials, and does not affect request success if session access fails. The local private header is consumed for correlation and excluded from upstream forwarding. Stable Pi affinity headers remain accepted as a fallback; per-request IDs are never promoted to sessions. Historical missing IDs are not backfilled.

DeepSeek Harness session correlation uses supported identifiers supplied by the client, or falls back off the forwarding path to Magpie-style read-only indexing of `$DSH_HOME/sessions/` (`Convs` / `SeedConvs` / `TurnConvs` / `ResponseIDs`) when Chat or Anthropic routes omit a session header. Connecting or refreshing the native route does not install a request-header script. Calls that remain unidentifiable or ambiguous across forked sessions are still inspected without misattributing session ownership; VaryAI does not substitute request IDs or cache keys. The retired `varyai-harness-session-id.mjs` script and `x-vary-harness-session-id` private header have been removed; native and standard client session headers (such as `x-deepseek-harness-session-id`) remain supported on ingress.

Managed T3 Code uses the Codex Responses driver and retains its native thread/session headers for correlation, with supported session metadata as a fallback. Stored event IDs use the `t3code_` prefix. Missing identities remain absent; request IDs, response IDs and cache keys are not conversation identities, and historical events are not backfilled.

OpenCode session correlation reads the installed client's native `x-opencode-session-id` and legacy/built-in-provider `x-opencode-session` headers, followed by its custom-provider `x-session-affinity` and `x-session-id` aliases. Native identity takes precedence over supported metadata. A present invalid or repeated native source leaves correlation unknown rather than merging another identity. Parent-session IDs, request IDs and prompt-cache keys are excluded. Audit/tool events use `opencode_`; the list and details also label existing raw IDs consistently without changing stored/filter identities or filling missing historical IDs. This shared extraction applies across supported operating systems and needs no client extension.

Hermes shared providers opt into its native `session_affinity_header` mechanism using `x-vary-hermes-session-id`. Hermes adds that client-declared conversation affinity on Chat, Responses and Anthropic requests; VaryAI consumes it before upstream forwarding removes private headers. Native `x-hermes-session-id` or Responses `session_id` values take precedence when supplied. This affinity can survive compression and follow the conversation root; Hermes may use a shared cron-job scope, so it is not a guarantee of the current physical transcript ID. VaryAI does not derive it from request IDs, prompt-cache fields or histories. Only the managed provider entries change, previous values restore on disconnect, and events/list/detail labels use `hermes_` without inventing missing historical identities.

TRAE's owned global Hook requires its native **Configured Hooks** switch to be enabled in each edition's Hooks settings. Writing `hooks.json` does not enable execution. Native global/project activation and sandbox settings remain user-controlled; test the warning independently of the tool command's eventual exit status. Inspect the native Hook execution log when no event arrives to distinguish an uncalled Hook, a sandbox/launcher failure and a failed local submission. Both editions' Chat continuation tracking uses only complete previously observed function payloads when the client rewrites IDs, preserving the original messages and existing ownership rejection rules.

TRAE session labels are edition-specific: domestic TRAE CN uses `trae_cn_` and international TRAE uses `trae_`, while internal Agent IDs stay `trae` and `trae-intl`. Native tool events, generic audit correlation and domestic legacy audit inspection share the same normalization. The event list/details recognize prior domestic `trae_` and international `trae-intl_` labels without rewriting stored historical identities or adding a second prefix.

TRAE explicit reconnect preserves compatible owned model IDs and overwrites their editable configuration. Native creates are sequential because overlapping writes can leave an incomplete catalog even when the calls report success. Creation uses one publication refresh after all additions instead of refreshing after each model. Native readback and credential proofs still determine successful delivery. Incompatible native identities use replacement with restoration of the preceding owned configuration. Doubao Work's explicit Restart and audit launcher now share audit-mode startup; restarting a running app must retain the same loopback-only audit arguments used for an initially stopped app.
