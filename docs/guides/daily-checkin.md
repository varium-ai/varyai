# Daily rewards and account selection

On **Tools / Agent**, select **Manual check-in** or **Automatic check-in** immediately before the Agent's model picker. In the compact Agent list, open its details to reveal the same controls. The panels use the workspace's compact controls and theme colors; account controls and reward details wrap to fit narrower windows.

The button shows **Automatic check-in** when any saved account for that Agent has automatic check-in enabled; otherwise it shows **Manual check-in**. Its label updates when the setting changes. Saved mode is independent of current client connectivity and credential availability: restarting VaryAI, closing a native client, or temporarily losing account access does not clear automatic check-in. Before preferences are available, the button shows **Check-in** without guessing a mode. When no account is available, the panel shows the saved automatic mode with its switch disabled; connection and sign-in outcomes remain separate. A newly selected account still needs its own opt-in.

Check-in panels start hidden. The same button expands or collapses the panel below its Agent row. Only one panel is shown at a time, without a second heading toggle or a separate home-page card. Collapsing a panel preserves the selected account and pending authorization; automatic check-in continues independently. Confirmed claims and existing check-ins disable the claim button and show **Checked in** for the current day or campaign window. The Agent row dropdown always remains available so users can inspect details, select accounts and change automatic mode, including after all accounts have completed check-in. It retains its **Manual check-in** or **Automatic check-in** label. Status refresh re-enables the claim button when the vendor reports the next eligible day or campaign window; it does not change the saved automatic mode.

| Client          | Daily reward                                                | Account selection                                                                                                          |
| --------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| WorkBuddy China | Official campaign status and claim                          | Current desktop login plus independent browser-authorized accounts; each has its own automatic switch and daily result.    |
| Doubao Work     | Official client's campaign SDK                              | Accounts already signed in to the connected native client; check-in switches to the selected account and leaves it active. |
| Qoder CN        | Current official claim-benefit campaigns                     | Current native login on macOS, with optional independent browser authorization as a fallback. Native refresh tokens are never rotated by VaryAI. |
| TRAE CN         | Official daily Credits status and claim IPC                  | Current account in the connected native client. No token is exported to VaryAI.                                          |
| ZCode           | Gift plans explicitly advertised by the official marketing feed | Current native login, read without rotating the client's refresh token. Verification remains in the official client.  |
| Codex           | No daily check-in reward documented in the official service | Use the existing ChatGPT/Codex authentication manager and account-specific quota views.                                    |

WorkBuddy's native account picker includes account contexts; its currently saved desktop session is not a reusable pool of independently authorized refresh tokens. Use **Refresh accounts** after changing the desktop login to immediately reload the account list and local check-in results. Refreshing does not claim a reward. Use **Add account** on the check-in card for each separate browser grant. After authorization, choose that account to claim manually or enable its automatic switch. Starting or completing authorization never claims a reward or enables automatic check-in.

Doubao Work keeps its saved accounts within the official client. Sign in there and refresh VaryAI's list. **Switch and check in** uses the official account switcher, waits for the selected login, and then requests its reward. The account stays selected afterward. Automatic check-in processes enabled accounts in sequence and leaves the last processed account active. Completed daily results are reused without switching. A refused switch never falls back to claiming for the previous account.

Doubao Work's card shows the official quota reward, consecutive check-in days and total check-in days when the campaign provides them. Refresh queries the current account without claiming or switching; saved daily results remain specific to their account.

Automatic check-in requires VaryAI to stay open. WorkBuddy's independently authorized accounts can be processed separately; Doubao Work also needs its connected native client. Records are local to the device and separate from synchronized settings. See [WorkBuddy](workbuddy.md#daily-check-in) and [Doubao Work](doubao-work.md#daily-check-in-and-accounts) for credential handling and retry behavior.

Codex usage limits reset according to the subscription and usage window. Purchased credits and service promotions are different mechanisms. The [official pricing and usage documentation](https://learn.chatgpt.com/docs/pricing) does not document a daily reward to claim. VaryAI therefore does not offer a synthetic Codex check-in action.

## Qoder CN, TRAE CN and ZCode

Qoder CN's [official daily campaign](https://docs.qoder.cn/events/100credits) currently offers personal accounts 100 Credits per window, starting at 10:00 UTC+8. VaryAI reads campaign IDs, eligibility, amounts, claim state and expiration from the service rather than treating midnight as the reset. Expired, future and unrelated campaigns are never claimed. An absent campaign is checked again within 30 minutes. Only an explicit `CLAIMED` response confirms a new claim.

On macOS, VaryAI prefers Qoder CN's current native login. It reads the installed `product.json` to find the actual Electron application name and authentication directory; the Keychain entry is named from `electronApplicationName`, which can differ from the window title. For Qoder CN 0.4.8, the service is `Qoder CN App Safe Storage` and the account is `Qoder CN App Key`. The existing `v10` record is decrypted locally with the OS-approved secret, and only the current access token is used. The native credential file is never rewritten, its refresh token is never used or copied, and an expired native token is left for Qoder to refresh. Account identity is reread after each reward request.

Background reads skip Keychain entries that require authentication. If access is protected, **Read client login** can request the system's permission to read that existing entry; it does not start another Qoder login. The secret remains in memory for the current VaryAI process and is passed privately to its helper, never to the renderer or synchronized storage. A fixed source label distinguishes the native login from an independent backup account.

Once authorized, ordinary refreshes, claims, and repeated **Read client login**
actions reuse that process's cached secret instead of forcing another Keychain
read. A changed Safe Storage service or a rejected cached decryption key invalidates
the cache. Restarting VaryAI starts a new cache; macOS may require authorization
again for the first read. VaryAI does not change the Keychain item's access rules
or retain the native decryption secret across restarts.

**Add account** optionally authorizes an independent backup account. It opens the official account-selection page, creates VaryAI's own PKCE device login and stores the resulting device credential privately. This is a separate Qoder login credential used only by the rewards module, not a restriction on the permissions granted by Qoder's device authorization. Starting, completing or canceling authorization does not claim a reward or enable automatic claims. Cancel discards the pending verifier. **Remove backup authorization** deletes only VaryAI's local grant and disables that account's automatic claims; it does not clear the native login or revoke the grant at Qoder. The installed client's native machine identity helper is required.

TRAE CN uses the existing, explicitly connected local bridge. Open the native client and refresh VaryAI's panel after changing accounts. Its [official changelog](https://docs.trae.cn/ide_changelog) documents check-in promotions; amounts and availability vary. VaryAI invokes only the native daily-credit status and claim methods, never lottery or paid actions. The account identity is checked again before a claim and after the response. Ineligible accounts and service verification requests are shown separately from success.

ZCode's [official trial quota](https://zcode.z.ai/en/docs/welcome) resets automatically and is not a check-in action. Separate gift plans can arrive through its [marketing action contract](https://github.com/zai-org/ZCode/blob/main/docs/marketing-touch-client.md). VaryAI follows only explicit `claim_zcode_plan` actions, sends the actual installed app version and native device identity, and does not fabricate eligibility. Code `3007` requires verification in the official client; `1003` means already claimed and `1004` means ineligible. Reward quantities are omitted when the service supplies none. No active offer is a normal state, not a successful claim.

Qoder CN and ZCode require an installed Node runtime with built-in Fetch support (Node 18 or newer). TRAE CN uses its native bridge runtime. Native acceptance has not been established for Windows or Linux. Native client schema changes or unavailable runtime/device identity produce an unavailable status rather than a synthetic success. Claims are optional and independent of model routing. Refresh is read-only apart from refreshing VaryAI's own authorized Qoder device credential. Automatic claiming is off by default, bound to the account for which it was enabled, and requires VaryAI to remain open. TRAE CN additionally needs its native client open. Successful records expire at the official activity boundary; inactive campaigns and failures use a retry delay, and one unavailable vendor does not stop the others.

Native macOS acceptance on 2026-11-05 covered all five check-in buttons, expansion and account/status rendering in the running development app. Qoder CN 0.4.8's authenticated campaign query confirmed an already claimed 100-Credit window. TRAE CN 3.4.15's current account claimed 200 Credits through the native IPC, with automatic check-in remaining off. ZCode 3.16.3's native account query returned no active gift offer; a live ZCode claim could not be exercised without an eligible offer. Its claim outcomes and verification handoff are covered with synthetic protocol fixtures.

The subsequent Qoder native-account acceptance, including the installed client's update to 0.5.3, showed **Using the current Qoder CN login** and the same confirmed 100-Credit window in the running app, without opening a browser login or authorization page. A rebuilt development app required the user to approve Keychain read access again; the background query returned promptly without prompting, and the explicit read action completed after system approval. Synthetic encrypted fixtures additionally cover native-first selection, fallback grants, expired credentials, stale account selections and preservation of the native credential file.

As of 2026-11-05, the remaining integrated Agents—Claude Desktop, Claude Code, Codex, Gemini CLI, Grok Build, Pi, Hermes, OpenCode, OpenClaw, Kimi Code, Qwen Code and DeepSeek Harness—have no confirmed official claim-based reward endpoint in this audit. VaryAI does not add a check-in button for automatic quota resets, subscriptions or unverified promotions. For example, [Kimi Code membership limits](https://www.kimi.com/code/docs/kimi-code/membership.html) are usage allowances rather than a daily reward claim. The [Qwen Code setup guide](https://qwenlm.github.io/qwen-code-docs/en/users/quickstart/) also states that its former OAuth free tier ended on 2026-04-15; it is not a current daily reward. Recheck official campaigns before adding further adapters.
