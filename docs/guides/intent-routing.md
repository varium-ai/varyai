# Codex intent-routing configuration

## Current development scope

Open **Settings → Routing → Codex routing groups**. This includes a configuration editor, an offline plan validator and an explicitly authorized network classification trial. Saving alone does not start routing. When the unified Codex routing switch is already authorized and on, available groups are automatically synchronized to its model menu. Temporary CLI sessions can also execute real Responses requests after separate consent.

- Create, edit and delete up to 32 draft groups, each with up to 16 model members and 16 ordered intent rules.
- Members reference existing Codex providers and exact upstream model IDs. No credentials are copied into routing groups or returned by the provider-options command.
- Choose a default member and explicitly approved fallback members. Fallback order follows selection order. The planner deduplicates members and keeps each candidate's own model ID.
- Rule descriptions are sent only during an explicitly authorized classification trial or temporary execution session with intent recognition enabled. Optional classifier settings reference a separate Codex provider configured for Chat Completions.
- The persisted `enabled` flag remains reserved and must be false. Saving does not start the proxy, take over Codex or change the current provider. An already authorized model-menu connection synchronizes saved group changes automatically.

Draft task members may reference any existing Codex provider, including official accounts and managed OAuth accounts. Authentication type does not restrict draft membership or catalog discovery. Members that fail the current transport configuration check remain editable and show a notice in the group list and editor.

Offline plan validation still requires task providers to explicitly declare `openai_responses` with stored API-key credentials. Classifier providers must declare `openai_chat` with stored API-key credentials, including when saving drafts. Temporary execution separately resolves native official and managed OAuth account credentials; the offline validator remains API-key-only. These configuration checks are not evidence that a model supports tools, images, reasoning, or inference access.

## Compact list

Routing groups use a single divided list with a two-line name/member summary, a public alias and a compact strategy selector. Each row uses the registered Agent icon for its explicit `client` association, with the generic box as fallback for missing or unknown clients; model names and providers do not determine the icon. Filter locally by group name, exact model ID text or provider name; filtering never changes saved groups. Editing and confirmed deletion remain available per row. Selecting a strategy saves a user-owned group override. Member information checks supported task transport and locally available official/OAuth identity, rather than the older API-key-only offline validator. It does not prove inference permissions or remote availability.

Editing follows Magpie's in-place row expansion: click the group name, alias, Agent icon, member summary, blank row space or existing Edit action to open it, and click the editor heading to fold it. The heading also accepts Enter and Space. There is no separate expand/collapse button. Strategy, readiness and delete controls do not trigger row editing. Only the selected row becomes an editor, while the other rows, filter and list toolbar stay visible. New-group editors appear above existing rows. The open editor stays mounted when filtering, even if it no longer matches. Save or Cancel folds it back into the list; a failed save keeps the draft and displays a sanitized error inside the editor. Opening another group or starting a new one confirms discarding unsaved configuration changes. Unchanged drafts can fold directly; changed drafts ask the user to Save or Cancel first. Focus moves to the group name on open and returns to the row's Edit button on close, or to Create group if the row is filtered out. While editing, strategy shortcuts, deletion and automatic-discovery toggles are disabled to prevent conflicting configuration changes.

Row expansion uses Magpie's measured-height motion: a 570 ms damped spring (response 0.42 s, damping 0.8, roughly 1.5% overshoot) opens the slot, and a 420 ms `cubic-bezier(.32, .72, 0, 1)` folds it. CSS `linear()` uses the sampled reference spring where supported, with the reference cubic fallback otherwise. The editor heading and fieldset sections enter individually from `translateY(-6px)` and zero opacity over 420 ms, staggered by 18 ms after an initial 40 ms delay (capped after twelve sections). This avoids fading the entire form as one panel. The summary fades back over 300 ms after a 90 ms delay, matching the reference's fold rather than crossfading two overlapping editors. Content entrances finish independently of the slot height, so later sections do not snap visible when height motion ends. Reference: Magpie revision `508911e431f752052d1c8374f89de7ec75f291ac`, `internal/gui/assets/app.js` and `internal/gui/assets/plugins/routing/client.js`; attribution is retained in `third_party/magpie/LICENSE`.

The list below moves with the row's actual height rather than a scaled screenshot. Closing immediately unmounts form controls and revokes temporary execution sessions. Focus uses `preventScroll` without scrolling clipped controls into view. When closing from an editor's foot, the nearest scrolling container follows the row's shrinking height to keep its summary visible. Explicit user scrolling interrupts that follow, and the container's original anchoring and scroll behavior are restored afterward. Opening preserves the reader's scroll position.

A new editor grows from zero; a cancelled new editor shrinks to zero before its empty slot is removed. Interrupted transitions restart from their currently visible height and are cancelled on unmount. Ordinary field edits do not replay the animation. System reduced-motion preferences disable all transitions, including changes made while one is running. Unsupported or failed animation APIs fall back to a functional instant transition. Natural height and overflow resume after the transition, so the row can grow with validation and trial output.

## Automatic group discovery

The **Automatically create routing groups** switch is off by default and persists independently of proxy activation. When enabled, the list derives draft groups from saved Codex `modelCatalog.models[].model` entries and account-scoped official model discovery caches. Enabling the switch or selecting **Reload** fetches official catalogs; ordinary list reads never perform network discovery. No inference requests are made.

All Codex providers with saved model catalogs participate, including official and OAuth accounts and providers whose transport configuration is not yet supported. API-key providers without saved catalog entries contribute no models. Official accounts can instead contribute models fetched from the fixed ChatGPT Codex models endpoint. Discovery normalizes vendor spelling following Magpie's `sameModel`: lowercase, remove vendor path prefixes, collapse spaces/underscores/dashes, equate digit-separated dots or `p` with dashes, and remove compact six/eight-digit snapshot suffixes. Dashed OpenAI dates, four-digit releases and variants such as `:batch`, `-thinking` and `-flash` remain distinct. This is spelling normalization, not inferred semantic equivalence. Every member retains its exact original model ID for forwarding.

Duplicate rows from one provider count once. At least two distinct providers are required. Members follow provider sort order with stable creation/ID ties. Storage IDs remain hashes; public automatic aliases are readable, for example `auto/gpt-5.6-sol`. Catalog display names are preferred over raw IDs, including names retained in account-scoped official caches. Existing saved groups without a public alias retain `vary-auto/<group-id>`. Legacy exact-ID manual overrides and deletion records suppress corresponding normalized auto groups, avoiding duplicate or resurrected entries.

Automatic groups are not persisted as separate configuration rows. Editing and saving one creates a user-owned override that survives switching discovery off. Deleting an automatic group or its saved override records a hidden ID, so refreshes and off/on cycles do not recreate it. Catalog changes are reflected when the list reloads; use **Reload** to refresh official account models and reread saved API-key provider models. Existing user overrides are never regenerated from the catalog.

The combined list shows at most 32 groups, with saved groups taking priority. Automatic groups with more than 16 providers are omitted instead of silently discarding members. The interface reports the number omitted. Import/restore turns automatic discovery off while preserving hidden IDs and saved drafts. Discovery alone does not start execution. With the unified Codex routing switch already on, available discovered groups are automatically published alongside provider models.

## Group scheduling

New automatic groups default to **Smart**. Existing saved groups without a strategy retain **In order** for compatibility. The compact list and editor expose the nine Magpie routing choices:

- **Smart:** defer quota windows at 90% and 98% utilization. Among accounts with room, prefer the largest window's earliest hourly reset, then smaller windows. Spent accounts with usable credits precede those without. Unknown/stale quota stays stable behind known healthy accounts.
- **In order:** try the configured default and approved fallbacks in order.
- **In turn:** rotate the first candidate for each unbound selection.
- **Least used:** compare reported quota utilization, then recently routed tokens with a one-hour half-life. Usable credits break ties among spent accounts.
- **Use before reset:** compare remaining allowance per hour until reset, using day-or-longer windows when present and the tightest budget. Healthy rates within ten percent share a band and prefer lower recent token use. Low/spent tiers follow Smart. Unknown official allowance assumes a full week; an API key without windows has no allowance pace.
- **Free first:** explicitly free models first, then paid/unknown models, each in configured order. Use the model catalog's boolean `free`/`is_free`/`isFree` metadata, a complete explicit zero-price table (`pricing`/`price` with input, output, cache-read and cache-write prices), or a nullable member override. A member override takes precedence; incomplete prices stay unknown. Never infer free usage from names or subscription tiers.
- **Speed first:** compare streamed first-content latency plus the estimated time to write 200 tokens. Output rate excludes hidden reasoning; buffered bursts and non-streaming replies do not manufacture a speed. Ten-percent bands retain configured order. Every fifth selection with both measured and unmeasured awake routes puts an unmeasured route first, rotating probes. These are ordinary user requests, not extra inference calls.
- **By weight:** smooth weighted rotation with member weights from 1 to 1000 (default 1). Cooling-down members sit out. Charge the route that actually answered, including affinity, rule preference and failover.
- **Manual:** select a member directly in the compact row or editor. Pause intent classification and rule selection and disable cross-member fallback, even for 429/5xx responses. Only the chosen member must be executable; unavailable inactive members or a paused classifier do not block the group. Menu reasoning/image capabilities describe the chosen member. Keep existing continuations on their original account rather than moving opaque state to a new member. Stored rules remain available when switching back.

All strategies retain the final ready/resting partition. Only approved candidates participate, and an intent rule's selected member remains first except in Manual mode. Continuation/account binding overrides scheduling. Ambiguous failures and bound requests are never replayed at another account.

Quota and credit data comes from the official fixed `/backend-api/wham/usage` endpoint, response headers and supported rate-limit events. Samples expire after five minutes or their reset. Recent token counts and exact-account/model speed averages are in-memory, bounded by published sessions, and reset on restart. Speed samples use a twenty-minute half-life and expire after an hour. Preparation and telemetry failures never interrupt forwarding; no database access or usage-history scan is added to selection. Direct entries and groups share telemetry. Compatible refreshes preserve bindings and telemetry across strategy, weight, cost and manual-pick changes; destination/account changes do not inherit them.

This aligns the nine strategy algorithms for the supported Codex transport with Magpie revision `508911e431f752052d1c8374f89de7ec75f291ac` (`internal/routes/strategies.go`, `fastest.go`, `round.go`, and `internal/gateway/speed.go`). It does not add Magpie's other-client allowance adapters, reset-card redemption, nested groups or per-turn affinity modes.

## Official account discovery and cache

- An unbound **OpenAI Official** card follows the native Codex `auth.json` ChatGPT access token and workspace; it does not silently use the managed OAuth default account. This first implementation supports file-based credentials only. Keyring, auto/keyring-first, ephemeral credentials and official API-key login are not supported by this discovery path. An unavailable status asks the user to check login/storage/network; native token refresh remains Codex's responsibility.
- A card explicitly bound to a managed Codex OAuth account uses that account. An unbound `codex_oauth` provider uses the manager's default. Missing or reauthentication-required accounts do not fall back to another account. The existing managed OAuth token manager handles necessary token renewal.
- Fetches use the fixed official endpoint, disable redirects, have bounded concurrency (four providers), a 30-second per-provider operation deadline and a 2 MiB response limit. Errors expose no upstream response bodies or credentials. The UI shows updated counts, valid-cache fallback or unavailable for each account provider.
- Discovery and official forwarding share a Codex client-version resolver, with a `0.165.0` compatibility floor. Like Magpie, it selects newer local version evidence instead of always advertising an older hardcoded client. Passive preparation reads only the `client_version` field of Codex's bounded cache and the version of installed `@openai/codex` packages; it never executes a CLI. Authenticated routing requests from a Codex user agent may raise the in-memory version. File probing is cached for ten minutes and runs off the forwarding path. No models or account data are imported from Codex's cache. After updating the Rust backend, select **Reload** to replace an existing account catalog fetched under the old identity; merely refreshing the page reuses the current account-scoped cache. Model availability still comes from the account's actual upstream response, not a hardcoded model list.
- Successful catalogs are cached for up to 24 hours in extension preferences (`model_cache:<identity hash>`). Native cache identity includes a token fingerprint and workspace; managed identity includes local account ID, authentication generation and workspace. A native token rotation therefore requires another reload. Cache entries contain only model IDs, timestamps and hashed identity, never credentials. The history is bounded to 64 entries and import/restore clears these caches.
- Failed fetches preserve a still-valid cache for the same identity, not a different account. Explicit user-saved catalogs remain separate and available. Codex's `models_cache.json` is not imported because its account provenance is not reliable. Provider settings and Codex client files are not updated with discovered models.
- Refreshing a catalog does not validate inference access, start routing or switch providers. It synchronizes an already authorized model menu. The running application's Rust backend must include this change; frontend hot reload alone cannot add the new command.

## Offline plan validation

Open a draft and enter a synthetic JSON classification result:

```json
{ "intentId": null }
```

Replace `null` with an enabled rule's stable ID, shown in the editor, to inspect its preferred member followed by approved fallbacks and the default member. The backend rejects unknown or disabled IDs, missing or duplicate fields, extra fields, explanatory prose and responses over 4 KiB.

This operation makes no network calls. It does not classify arbitrary user messages or verify real traffic. Editing the configuration or test input invalidates the result; late replies cannot replace the newer editor state.

## Network classification trial

Configure a Chat Completions API-key classifier in the group editor, enter synthetic task text, review the displayed provider/model and check outbound consent before running. The call may incur charges. Saving never sends text. Editing group fields or test text revokes consent and invalidates late results.

Only test text and enabled rule descriptions are sent with the classifier's own credentials. The trial never reads conversation history, activates routing, switches accounts, changes client files or forwards tasks. Official/OAuth task members may appear in the proposed plan: this is not transport readiness validation. The offline validator remains unchanged.

Independent privacy inspection runs even if business auditing is disabled. Enabled audit/allow rules become redaction rules; block rules remain blocking. Both text and descriptions are inspected. Redaction precedes Unicode-safe truncation to 4,000 scalar values (first 3,000 and last 1,000). Limits: 32 KiB payload, 64 KiB response, 4 KiB classification content, four concurrent trials and the configured 500–5,000 ms deadline including preparation. No redirects or retries. Detection cannot guarantee finding every secret; use synthetic examples.

Only strict `{ "intentId": "enabled-rule-id" }` or `{ "intentId": null }` output is accepted. Unknown IDs, extra fields, tool calls, refusals and truncated responses are rejected. Errors, timeout and privacy rejection return the default candidate order and a fixed reason, never raw responses. VaryAI does not persist trial text or results.

The Responses extractor excludes instructions, attachments, tool payloads and unknown continuations. Temporary execution uses it only for unbound initial classification; bound continuations do not trigger classification.

## Storage and safety

Configuration is stored in `intent_routing_groups` in the extension database `vary-ai.db`, schema version 5. The public shared schema follows released CC Switch version 23. Historical intent-routing extension versions 3 and 4 upgrade without losing saved groups or preferences. Members and ordered rules are stored inside one versioned JSON document per group, making each update atomic without duplicating credentials. Updates and deletes require the current revision to prevent lost edits.

Existing database export, sync and backup mechanisms include draft configuration. Import/restore validates group structure and disables group activation and intent recognition. Provider existence is rechecked on draft save; plan validation additionally checks task transport configuration. Stale references are not evidence of readiness. No prompts, classification history or decision records are stored by this phase.

## Temporary Codex execution (experimental)

Open a valid group editor and expand **Temporary Codex execution**. Enable the local proxy first, confirm outbound consent, then create a session. Run the displayed macOS/Linux command in a new Codex CLI conversation. It selects the group's public alias (`auto/<model>` or the existing `vary-auto/<group-id>`) with per-process `-c` overrides and an environment credential. The command also sets `model_catalog_json` to a private temporary file containing only this session's group, with the same capability-derived reasoning levels and image policy used by the full model menu. This makes `/model` display the selected group instead of the built-in provider list. It does not publish every saved group or provider model; use the Codex routing switch for that combined menu. No global `config.toml`, `auth.json`, persistent model catalog or current-provider setting is changed. Keep the editor open: editing/closing it revokes the session. The token otherwise expires after one hour, or when VaryAI exits. Temporary catalogs are private (0600 on Unix), contain no token or upstream credentials, and are removed on explicit revocation, expiry or normal runtime shutdown. Failed session installation removes its catalog too. Expiry timers are canceled when the session is removed and do not keep the runtime alive. An in-flight request may finish after revocation.

- Separate `/intent/v1/responses` and `/intent/v1/models` endpoints accept only the random local session token; browser-origin requests are rejected. No gateway-key budget is implied by this credential.
- Preparation reads providers off the forwarding path and freezes account credentials, exact model IDs, endpoint and classifier configuration in memory. Native official accounts use file credentials; managed accounts resolve their explicit/default account once. A later account/default change never redirects an existing session. Tokens are not persisted; managed credentials can refresh only for the frozen account identity. Native login changes and session expiration require a new session. Startup currently caps sessions at 16, each for one hour.
- API-key members must explicitly declare native Responses. Official/OAuth members use the fixed ChatGPT Codex endpoint with their own bearer token, workspace and client headers. Native official execution requires the caller to send `stream:true` and `store:false`; unsupported semantics are rejected, not silently rewritten. Inference permissions still require live validation.
- Initial requests may classify sanitized supported user text, then apply the configured strategy within the approved plan, keeping an intent rule's selected member first. A received 429/502/503/504 may try the next candidate before any output is delivered. Ambiguous connection failures, other errors and any bound continuation are not replayed at another account. Error responses are fixed codes without upstream bodies.
- The first implementation conservatively pins the entire client conversation, not just one tool turn. Response IDs and function-call IDs also pin the exact candidate. Unknown/conflicting continuations or opaque state without a known binding are rejected. Overlapping requests under one session token receive 409 rather than racing. Bindings are memory-only and bounded to 4096 entries; restart/expiry does not silently reconstruct them.
- JSON and SSE bytes pass through unchanged. A bounded observer records response/tool IDs; duplicate IDs from different targets become unusable rather than overwriting ownership. Request edits preserve untouched JSON lexemes. Caller credentials/cookies/workspace headers never become upstream authentication. Business security inspection, tool observations and asynchronous completed-usage accounting remain connected.
- The local test suite covers model-specific fallback, credential stripping, JSON/SSE tool continuations, unknown/colliding IDs, account snapshots and revocation using synthetic accounts and dynamic ports. No real paid inference or installed-app acceptance is implied.

## Codex model-menu takeover

In **Settings → Routing → Local routing → Codex**, enable the single Codex switch and confirm configuration changes, forwarding and classification costs once per connection. The local gateway must already be running. There is no Current provider / Routing groups mode picker, group-publication checklist or separate connect button. The confirmation also authorizes automatic menu updates for subsequent group additions, edits, deletions and discovery changes while routing remains on. Saving configuration with routing off never starts forwarding.

One dedicated `varyai-routing` provider and one external Codex-native catalog expose both kinds of entries:

- `vary-provider/model-<hash>`: **exact model ID · provider name**. The hash is derived from the exact provider ID and model ID. Each entry has one isolated target and never runs intent classification or another provider's fallback.
- `auto/<model>` for newly discovered groups, or the existing `vary-auto/<group-id>` alias for older/manual groups: **group name · routing group**. Selecting it uses that group's strategy, approved candidates and optional intent classification.

The menu includes executable Responses API-key providers and available official/managed OAuth accounts. Models come from the provider's configured model, its saved/discovered catalog and referenced group members. Unknown protocols, unavailable credentials and non-executable groups are omitted, with a count in the UI; discovery is not evidence of inference permission. At most 256 entries are published, reserving room for the routing groups. The current provider's configured/first model is the initial default when available; it is not a global override for explicitly selected provider or group entries. Enabling routing does not change the homepage's current-provider setting.

Reopen Codex and start a new conversation after enabling routing. Selected profiles, workspace overrides and existing conversations may retain their previous provider or catalog. Actual Codex desktop acceptance must be verified with the user's client version.

The local credential and recovery receipt are private (0600 on Unix) and contain no copied upstream credentials. Publication does not write `auth.json`. A legacy ordinary takeover is restored before the unified owner is installed, under the same Codex switch lock; failed activation attempts restore the previous owner without stopping the listener. Changes are limited to the selected model, model provider, catalog pointer, web-search setting and one owned provider table. The catalog uses the native Responses template, a conservative 32k context, capability-derived reasoning levels and image policy, and shell-based edits. No capability is inferred from a name. Standalone search and WebSockets are disabled for this HTTP/SSE-only path.

Configuration writes journal a durable receipt before replacing `config.toml`. A no-clobber install rejects concurrent replacements. Restore returns the exact original file when unmodified; otherwise it restores only still-owned fields, including owned model aliases selected in Codex, and preserves unrelated/newer edits. Catalogs have unique names and are retained until disconnect; unchanged refreshes reuse the existing file. At most 64 distinct catalog versions are retained per connection. Interrupted updates record the previous projection. Symlinked/oversized files and overlapping ownership are refused; external edits are never force-overwritten.

Turning the Codex switch off, stopping the gateway or normal VaryAI shutdown restores the original configuration. Startup attempts recovery before importing live configuration after a crash. Failed recovery keeps its receipt and exposes a recovery action. Reconnect explicitly after restart; existing Codex processes may retain an old local token. In-flight requests may finish after disconnect.

Every provider entry and routing group has an independent runtime snapshot and continuation-binding store, with no one-hour menu expiry. Group save/delete, discovery toggles and explicit catalog reload automatically rebuild the authorized menu. The local token and continuation bindings survive refresh only for unchanged group configuration and identical account/model destinations. Changed destinations cannot inherit old response/tool bindings. Failed synchronization leaves the saved configuration intact but revokes the stale runtime and exposes recovery rather than continuing to forward to deleted/stale targets. Disconnect/recover and enable again after resolving the problem.

Managed identities are frozen at connection time; refreshed credentials must still match that identity. Native login changes fail closed. Provider editing/switching and listener-address changes remain blocked while this configuration is owned; disable Codex routing first. Provider models and routing groups coexist in Codex's menu without allowing two independent writers to own its configuration.

Tests use temporary config directories and synthetic accounts, covering menu aliases, exact JSON/SSE forwarding, cross-group continuation rejection, explicit consent, private-file modes, crash recovery, newer external edits and gateway shutdown restoration. The implementation follows the documented `model_catalog_json`, `model_providers`, bearer-token and native Responses configuration fields: https://developers.openai.com/codex/config-reference/ . No real login file was changed during verification.

## Remaining before live acceptance

Per-turn reselection, concurrent subagent conversation identity, compact/image/search endpoint routing, richer response header propagation and real Codex desktop/official-account acceptance remain unfinished. Model-menu publication/restoration is implemented; managed account tokens can refresh without following a changed default, while native login identity/token changes require reconnecting. Persistence still rejects `enabled:true`; execution is authorized by the unified Codex switch or a separate temporary-session consent, not by the stored flag.
