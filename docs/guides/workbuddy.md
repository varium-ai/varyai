# WorkBuddy provider configuration

VaryAI lists two independent tools: **WorkBuddy China** (`workbuddy`) and **WorkBuddy AI** (`workbuddy-ai`, international). Their website and installation shortcuts open [workbuddy.cn](https://www.workbuddy.cn/) and [workbuddy.ai](https://www.workbuddy.ai/) respectively. Desktop presence and version checks use each edition's own bundle identity, including renamed bundles, and ignore applications in Trash. Uninstalling one edition does not change the other edition's installation state. An uninstalled edition shows only installation and website shortcuts under **More tools**, without check-in, model selection, routing switches, stale versions or connection status.

Connection failures appear below the affected Agent, including when its compact details are collapsed. Retrying that Agent clears its previous error; actions on other Agents do not clear it. Enabling either WorkBuddy edition writes the current shared catalog over native entries with the same model IDs, including stale entries left without a connection receipt. The connection receipt saves the previous configuration so disconnecting restores the overwritten models. Unrelated native models and the array or object document shape are retained. The same explicit-enable behavior applies across Agents. File access, directory overlap and concurrent-write failures report an error below the affected Agent.

Both tools can connect independently to the shared supplier and routing-group catalog. China uses `~/.workbuddy/models.json` by default; international uses `~/.workbuddy-ai/models.json`. The China edition retains its existing explicit directory override and legacy `.codebuddy` fallback, but never discovers the international directory as a fallback. International model configuration follows the [official WorkBuddy AI documentation](https://www.workbuddy.ai/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Model-Configuration).

Each connection owns separate local credentials, recovery receipts, model selections, routing scopes, usage and audit identities. Disconnecting one restores only its own managed fields. The two tools reject overlapping configuration paths or a recovery receipt that still owns the other edition's file; disconnect that previous connection before reconnecting, and correct any China directory override that points at the international directory. Existing configuration and credentials are not copied or moved automatically. The international tool uses the shared catalog connection; the China-specific provider configuration and daily check-in controls described below remain scoped to China.

VaryAI supports selectable official and API-key WorkBuddy configurations. Official mode uses the installed client's login state; API-key mode uses the configured endpoint, credential and model. Creating a duplicate provider does not switch the active configuration or write client files.

Enable takeover deliberately, back up the client settings and restart WorkBuddy when it needs to reread its endpoint. Disabling takeover or exiting normally restores the owned settings. An abnormal termination cannot perform normal exit cleanup; recovery uses the persisted backup at the next start.

When no official endpoint is set in `settings.json`, routing reads the newest product cache in the WorkBuddy configuration directory. Both `cache/acc-product-config-v3.json` and `cache/acc-product-config-v3-*.json` are supported. Start WorkBuddy first if no cache exists. An unreadable or invalid newest cache stops setup without changing client settings.

Switching suppliers replaces all identifiable VaryAI-managed models with the selected supplier's catalog. Switching to the official entry removes those managed custom models while preserving native login, settings and unrelated user models. A private `models.json.varyai-owned` file beside the native catalog records model IDs and SHA-256 ownership fingerprints, without plaintext credentials. It survives deletion of the shared database and participates in profile undo. Configuration changes restore the previous ownership file if the database commit fails. URL changes during routing do not change model ownership.

Historical models without ownership records cannot be identified after their database records are deleted. Import or resolve those native conflicts rather than deleting unrelated models automatically.

If adding a provider reports an existing model ID, use the saved provider or import the native configuration before editing it. WorkBuddy's native model catalog requires unique model IDs; adding the same IDs again does not select the existing provider. Click **Use this** on its card to make it current.

WorkBuddy displays each custom model as its name followed by its model ID. VaryAI uses the provider name for that display name without appending the ID again. To update labels written by an older version, edit the saved provider and save it again. Restart WorkBuddy if it still displays the old catalog. This updates display names while preserving model IDs.

The shared Agent catalog uses **Model · Supplier · VaryAI** consistently across clients, including WorkBuddy, Qoder and TRAE. Routing groups use **Group · routing group · VaryAI**. WorkBuddy, Kimi Code, Qwen Code and ZCode receive readable model IDs and names instead of internal routing hashes; duplicate labels receive short numbered suffixes. Kimi uses the readable name as its native model key, and the shared model-list endpoint publishes the same IDs for these clients. The connection receipt maps these readable IDs back to the unchanged internal routes, and older conversations can still use their original routing IDs. Refresh the connection catalog after updating VaryAI, then restart WorkBuddy if its picker still shows the previous labels.

Kimi Code desktop requires a positive `max_context_size` for every native model. Shared models with unknown upstream capacity use a conservative 32,000-token local ceiling; this does not assert or change the upstream model catalog capacity.

Shared ChatGPT/Codex official models accept all connected Agents' Chat, Anthropic and Gemini requests through the same protocol IR. The selected account keeps its existing identity checks, credential refresh and official transport; it is never treated as an API-key supplier. The upstream request uses Responses with `store: false`, streaming, instructions and required tool defaults. Unsupported official sampling and output-limit fields are omitted, matching the existing OAuth adapter. The response is converted back to WorkBuddy's requested Chat JSON or SSE format, including tool calls and usage. An omitted SSE media type is normalized only on this explicitly streaming official path; malformed or incomplete events still fail validation. Native Responses clients retain their existing request requirements.

The Codex tool's connection switch controls the Codex client itself. WorkBuddy does not require that switch to call a shared official model through its own enabled connection.

Completed official tool replies retain their encrypted reasoning privately within the current conversation scope, bounded to 64 replies and 2 MiB. Restoration requires the same prepared destination, exact tool identities and arguments, and an unchanged inspected visible summary. Other scopes, changed calls or summaries, conflicting observations and evicted state do not gain access to the cached reasoning. Ciphertext is never placed in WorkBuddy's visible messages. This in-memory helper does not recover hidden state after a restart.

WorkBuddy uses Chat Completions when selecting a native Gemini supplier. The [shared protocol IR](../architecture/protocol-conversion.md) carries reasoning effort, explicit off, budget and visible summaries independently, then builds Gemini's generation-specific `thinkingLevel` or `thinkingBudget` and `includeThoughts`. Responses-specific text settings remain eligible for Responses targets instead of being rejected by an unrelated intermediary format. A local `routing_conversion_unsupported` error indicates unsupported or malformed conversion semantics rather than an upstream credential failure. See [Gemini thinking controls](https://ai.google.dev/gemini-api/docs/generate-content/thinking).

Before cross-protocol conversion, both the shared Agent connection and the dedicated WorkBuddy route remove message-level host bookkeeping: Agent and request IDs, native response IDs and model labels, trace and step IDs, and usage records. Text-block `annotations` decorations are also omitted from the converted history. Inspection and session attribution still see the original request. Text, tool arguments, reasoning content and other model settings remain intact; same-protocol forwarding retains the native fields. Regression coverage includes the shared connection's streaming and non-streaming Gemini requests with these host markers, a prior assistant response, tools, reasoning and security inspection enabled.

When switching models through the shared Agent connection, WorkBuddy can replay complete visible Chat history, including plain reasoning and fully paired tool calls and results, to a single prepared destination. This includes switching from GLM or Gemini to a Responses-backed Grok model in the same conversation. Existing ownership is checked first; conflicting owners, busy scopes, changed saved destinations, incomplete calls and signed or encrypted state still fail closed. Imported call IDs are recorded only after a successful complete reply, including a reply that requests another tool, so later rounds retain their ownership. The original history remains available to security inspection and forwarding.

After enabling protection, restart WorkBuddy and open a new conversation before testing. The global protection confirmation includes this restart instruction. The saved takeover status means routing is configured; it does not prove that an already running client has reloaded its endpoint. If Security Center shows no WorkBuddy events, verify that new requests reach the local proxy before diagnosing individual detection rules. Optional catalog rules must also have Alert or Hide enabled; they default to Allow.

The active status requires a running proxy, a recovery backup, and the injected endpoint still present in WorkBuddy settings. A saved enabled preference alone is insufficient: after normal exit restores direct routing, enabling protection must apply the endpoint again. External changes to the endpoint also invalidate the active status.

Official forwarding retains the relevant login state. API-key forwarding uses the selected provider and strips official-only authentication data. Both follow the enabled inspection settings; a successful provider response is not a guarantee that every tool, payload or future vendor version is covered.

Use a disposable profile and explicitly synthetic message content when testing. Keep actual API keys and private settings out of prompts, logs and screenshots. Coverage and recovery behavior are implemented in [the takeover service](../../src-tauri/src/services/workbuddy_proxy.rs), [provider handling](../../src-tauri/src/services/provider/workbuddy.rs), and [proxy adapter](../../src-tauri/src/proxy/workbuddy.rs).

New suppliers are saved as inactive alternatives. Creating a supplier does not apply it to WorkBuddy; select it explicitly to replace the managed catalog.

## Daily check-in

The WorkBuddy page offers an account selector and **Check in now** for WorkBuddy China. **Add account** opens WorkBuddy's official browser sign-in; repeat it to authorize independent accounts. Choose an account before claiming its reward or changing its automatic check-in switch. Adding an API supplier does not authorize a check-in account. WorkBuddy AI's international campaign is outside this integration.

The current desktop login is also available. VaryAI reads `CodeBuddyExtension/Data/Public/auth/workbuddy-desktop.info` without changing it. It never copies or refreshes the native client's refresh token. Independent browser grants have their own refresh tokens, serialized refresh and private local storage, so they can renew without spending the desktop client's grant. Removing an added account deletes its stored grant and automatic check-in preference; it does not sign out the desktop client. An expired browser grant can be replaced by adding the same account again.

On macOS, encrypted credentials are decoded through the installed WorkBuddy runtime and its own credential SDK. The helper runs without a window and keeps decoded credentials in memory, returning them only through a private process pipe. It does not change credential protection or write plaintext back to the client. Device verification is requested through the installed native SDK when a check-in request is due; viewing local status never requests a device token. The installed client version supplies the request's User-Agent. If its SDK is unavailable or incompatible, the card reports protected credentials explicitly instead of asking the user to restart or sign in repeatedly.

Check-in queries the official campaign status before requesting a reward. The card distinguishes a claimed reward, an existing check-in, an inactive campaign, an ineligible account, an expired login, and an unconfirmed failure. Credit amounts and streaks appear only when the service supplies them. Device tokens come from WorkBuddy's installed SDK. If the official service still requires verification in its own client, the card says so; VaryAI does not synthesize device tokens.

The opt-in macOS acceptance test `cargo test --lib --manifest-path src-tauri/Cargo.toml live_native_workbuddy_checkin_status -- --ignored` uses the installed client and signed-in account to read the official campaign status. It does not claim a reward. Default tests use synthetic sessions and a fake runtime.

**Automatic daily check-in** defaults to off for each account. VaryAI processes enabled accounts separately while running, independently of the selected API supplier and local message routing. The previous single-account preference is bound once to its native account; it does not follow future desktop account switches. A native account that is no longer active is skipped. Browser accounts use their independently authorized grants. Closing VaryAI stops automatic check-in; it does not create an operating-system background task. The worker checks whether work is due every minute and retries unconfirmed failures after 30 minutes. Before noon Beijing time, an already-checked, inactive, or ineligible answer is checked again after 30 minutes because the vendor's campaign day may not have turned yet. A confirmed claim is reused for the rest of the Beijing day, including across restarts and concurrent manual actions. Manual retry can recheck other outcomes immediately.

Preferences and daily records live in `workbuddy-checkin.json` in Tauri's local application data directory, outside exported and synchronized configuration. Records use a SHA-256 account identifier and contain only preferences, dates, outcomes, credits and streaks. They do not contain tokens, names, raw vendor messages or client configuration. Independent browser grants and account labels are stored separately in `workbuddy-checkin-accounts.json` using atomic private writes (owner-only mode on Unix). These grants are local credentials, not encrypted native-client snapshots. Neither file enters configuration exports or synchronization. Unreadable storage stops check-in without overwriting it. Requests use the fixed HTTPS `copilot.tencent.com` endpoint, a 20-second request timeout and no redirects; client-customized model URLs never receive these credentials. Check-in failures do not interrupt normal message forwarding.
